# NeuroQuest — контекст проекта для нового чата

Репозиторий: https://github.com/KimDmitriyR/NeuroQuest.git (ветка `main`, 48 коммитов на момент написания)

Это образовательная квест-игра для подростков: физические карточки со
сканируемым QR-кодом запускают цифровой квест (чат-бот с ветвящимися
выборами) на 3 тематических сектора (финансы, кибербезопасность, ИИ),
плюс «конверты с миссиями» (физические задания с фото/шифро-проверкой), и
общий «мастер-код» из 12 букв, собираемый за прохождение всех карточек.

## Как продолжить работу в новом чате

1. Дай Claude доступ к git-репозиторию (клонировать
   `https://github.com/KimDmitriyR/NeuroQuest.git`) — у Claude нет своих
   git-credentials, поэтому для `git push` придётся присылать GitHub
   Personal Access Token (fine-grained, только на этот репозиторий,
   Contents: Read and write) прямо в чат при необходимости запушить.
2. Пришли этот файл (`PROJECT_CONTEXT.md`) и `CONTENT_SOURCES.md` — они
   дают полную картину: что сделано, какие решения приняты и почему, какие
   открытые вопросы остались.
3. Если работа продолжается с исходным контентом (докс-файлы квестов,
   миссий) — они больше не нужны повторно, весь текст уже перенесён в
   YAML (`backend/app/content/cards/*.yaml`,
   `backend/app/content/missions/*.yaml`) и закоммичен.

## Окружение для разработки (важно!)

У Claude в его песочнице **нет Docker** и не сохраняется состояние между
сообщениями одного и того же ответа (процессы вроде `uvicorn`, поднятые
в фоне, "умирают" между отдельными вызовами инструмента — сервер нужно
поднимать и тестировать в рамках одного вызова). Локальный Postgres
ставился через `apt-get install postgresql` прямо в песочнице для
тестирования, а не через `docker-compose.yml` (в котором есть только
сервис `postgres`, backend/frontend туда пока не добавлены).

### Реальная разработческая среда (для тебя):
```bash
git clone https://github.com/KimDmitriyR/NeuroQuest.git
cd NeuroQuest

# backend
cd backend
pip install -r requirements.txt
cp .env.example .env   # обязательно смени JWT_SECRET_KEY для не-дев окружения!
docker compose -f ../docker-compose.yml up -d   # поднимет только postgres
alembic upgrade head
python -m app.content.seed      # засеет все 12 карточек + 3 миссии
uvicorn app.main:app --reload   # http://localhost:8000

# frontend (другой терминал)
cd frontend
npm install
cp .env.example .env
npm run dev   # http://localhost:5173
```

Тесты бэкенда используют отдельную БД `neuroquest_test` (создать
аналогично `neuroquest` тем же пользователем/паролем), запуск:
`cd backend && python -m pytest -v`.

## Что уже полностью готово (46/46 backend-тестов, frontend build+lint чистые)

### Backend (FastAPI + SQLAlchemy async + PostgreSQL + Alembic)

Архитектура слоями: `models` → `repositories` → `services` → `api`,
Pydantic-схемы отдельно от ORM-моделей. Контент (тексты карточек и миссий)
хранится как YAML-данные (`app/content/cards/*.yaml`,
`app/content/missions/*.yaml`), загружается идемпотентным лоадером
(`app/content/loader.py`, `python -m app.content.seed`), а не хардкодится
в Python — так добавление контента не требует менять код.

**Модели/фичи:**
- `Player` — профиль ребёнка, принадлежит `ParentAccount` (обязательный
  `parent_id`)
- `ParentAccount` — email + bcrypt-хеш пароля, JWT-аутентификация
  (`/api/auth/register`, `/login`, `/me`, 30-дневный токен, HS256)
- Quest-граф: `Quest` → `QuestNode` (type: choice/completion) →
  `Choice` (текст, исход ✅/⚠️/❌, урок, достижение, разблокированный
  материал, `next_node_id`). `QuestCard` — физическая карточка
  (`qr_token`, привязка к `Quest` и `Sector`). Завершающая награда
  (финальный бейдж/анлок) висит на completion-узле, а не на выборе —
  выдаётся безусловно при завершении карточки, как в исходнике.
- `Achievement` — общий каталог, `is_badge` отличает финальные бейджи
  карточек от промежуточных мини-достижений. Один и тот же `Achievement`
  может быть закреплён и за выбором на этапе, и за завершением карточки
  (награда не дублируется — есть идемпотентная выдача через
  `PlayerAchievement` с уникальным constraint).
- `MasterCodeLetter` — 1:1 с `QuestCard`, `position` 1-12,
  уникальность позиции в БД. `PlayerMasterCodeLetter` — что игрок уже
  собрал (буква скрыта в API, пока не получена — не спойлерит фразу).
- `QuestSession`/`QuestAnswer` — прогресс прохождения и аудит-лог
  выборов.
- `EnvelopeMission`/`MissionAttempt` — конверты-миссии.
  `validation_type`: `photo` (всегда идёт на ручную проверку куратором,
  без CV) или `text` (авто-проверка, регистронезависимая). `text`
  поддерживает **многошаговую** проверку через
  `validation_config: {"steps": [{"cipher","answer"}, ...]}` и поле
  `MissionAttempt.current_step` — неверный ответ не наказывает, просто
  не продвигает шаг.
- Очередь проверки миссий (`GET /api/missions/attempts/pending`,
  `POST /api/missions/attempts/{id}/review`) требует токен родителя и
  **отфильтрована** по его собственным детям (join через
  `Player.parent_id`).

**API роутеры:** `auth.py`, `parents.py`, `players.py`, `quests.py`,
`missions.py`. CORS настроен на `localhost:5173`/`127.0.0.1:5173`
(`cors_allowed_origins` в `Settings`).

**Скрипт печати:** `backend/scripts/generate_qr_codes.py` — генерирует
QR-коды (кодируют `{base_url}/?quest=<token>` для карточек и
`{base_url}/mission/<uuid>` для миссий) и простые макеты лицевой стороны
карточек в `backend/print_assets/` (в `.gitignore`, генерируется заново
командой `python -m scripts.generate_qr_codes <base_url>`). Декодирование
всех 15 QR проверено `pyzbar`.

### Frontend (React + TypeScript + Vite + React Router + TanStack Query)

- `QuestChat` — **generic** компонент чат-интерфейса квеста, ничего не
  знает про конкретные карточки, полностью управляется JSON от API
  (важно: так и должно оставаться при добавлении новых карточек).
- `MissionFlow` — generic для photo (реальная камера через
  `<input capture="environment">`, base64 data URL, без файлового
  хранилища на сервере) и text/шифр (пошаговый ввод с обратной связью).
- Страницы: `HomePage` (обрабатывает `?quest=<token>` из QR и
  `?child=<id>` от родителя), `QuestPage`, `MissionsPage`/`MissionPage`,
  `ProfilePage` (мастер-код + достижения, кнопка гранд-финала при полной
  сборке), `FinalePage` (анимация сборки букв, эффект взлома, печатный
  сертификат), `ReviewPage` (очередь проверки для куратора),
  `ParentAuthPage`/`ParentDashboardPage` (вход/регистрация, список детей
  с мини-прогрессом, добавление ребёнка, ссылка активации устройства
  ребёнка через `?child=`).
- `api/client.ts` — единая точка HTTP, автоматически добавляет
  `Authorization: Bearer <token>` из localStorage
  (`neuroquest.parent_token`) ко всем запросам — компоненты не думают
  про авторизацию отдельно.
- Дети **не могут** сами себя создать (раньше могли, потом убрал) —
  профиль создаёт только авторизованный родитель через кабинет; ребёнок
  получает `player_id` через ссылку `?child=<id>` или прямо на общем
  устройстве кнопкой «Играть на этом устройстве».

Подробности и источник каждого решения — см. `CONTENT_SOURCES.md`.

Ключевое: мастер-код всех 12 карточек собирается ровно в
**«ТВОЙНОВЫЙКОД»** (проверено сквозным regression-тестом
`test_full_playthrough.py` — один игрок проходит все 12 карточек, всегда
выбирая первый вариант, и получает полную фразу).

## Известные ограничения и открытые вопросы

1. **Реальный браузер ни разу не запускался.** Весь фронтенд проверен
   через `tsc`, `vite build`, `oxlint` и точное соответствие
   TypeScript-типов API-контрактам бэкенда — но не кликами в настоящем
   браузере/на телефоне. Это первое, что стоит проверить.
2. **Docker для backend/frontend не написан** — `docker-compose.yml`
   поднимает только Postgres. Нет `Dockerfile` ни для backend, ни для
   frontend.
3. **Миссия 2 «Энигма»** — контент (4 шифра Цезаря) есть и работает, но
   физический реквизит (диск-шифратор), судя по переписке с заказчиком,
   мог быть ещё не готов на момент написания. Уточни у владельца проекта
   актуальный статус перед печатью материалов.
4. **Грандфинал-приз** — в исходнике раздел про финальный приз помечен
   автором как черновой ИИ-брейншторм («все придумал ии»), поэтому в UI
   сделан честный плейсхолдер «Финальный приз скоро появится здесь»
   вместо выдуманного промокода/скидки. Нужно реальное решение по призу
   от владельца продукта.
5. **`JWT_SECRET_KEY`** в `.env.example` — dev-заглушка
   (`dev-insecure-secret-change-me`), обязательно сменить перед любым
   не-локальным использованием.
6. Цвета секторов (`color_token`, hex) — плейсхолдеры моего выбора,
   исходник называет только словесно («Неоново-бирюзовый» и т.п.), точный
   hex не задан. Заменить на дизайн-система значения, когда появятся.
7. `POST /api/quests/start`, `/choices`, миссии — принимают `player_id`
   без проверки, что вызывающий действительно владеет этим игроком
   (только создание игрока и просмотр очереди проверки защищены). Для
   продакшена стоит расширить авторизацию на игровые эндпоинты тоже.
8. Нет rate-limiting на `/api/auth/login` — возможен брутфорс пароля.

## Стиль работы, который стоит продолжать

- Маленькие частые коммиты с понятными сообщениями (см. `git log`), не
  большие "мега-коммиты".
- Перед изменением схемы БД — реально применять миграцию и проверять на
  локальном Postgres, не полагаться только на код.
- Перед любым API-изменением — проверять живым HTTP-запросом (curl),
  не только юнит-тестами.
- Реальный контент карточек/миссий — только из присланных исходников,
  противоречия/пробелы в исходнике фиксировать явно (в комментариях
  YAML и в диалоге), а не додумывать самостоятельно.
